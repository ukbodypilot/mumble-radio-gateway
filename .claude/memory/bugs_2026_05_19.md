# D75 Watchdog Silently Dead — The Stale Plugin Bug (2026-05-19)

## Symptom

For ~6 weeks the user reported D75 BT serial dropping multiple times per day. Multiple "fixes" pushed: try/except around watchdog loop, heartbeat log every 60 s, malloc_trim cleanup, etc. **None of them ever appeared in journalctl** — zero `[D75-WD]`, `[D75] Watchdog: alive`, or any other new instrumentation lines. Plugin kept running but watchdog was effectively dead. PTT commands returned `{ok:False, error:'serial not connected'}` for hours at a time, recovered only when the user manually restarted the plugin.

## Root cause

`tools/link_endpoint.py` had:
```python
sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
```

That puts the parent directory (`/home/user/link/`) at `sys.path[0]`, *before* Python's default of the script directory (`/home/user/link/run/`). The deploy mechanism syncs new plugin code to `/home/user/link/run/`. But Python's `from d75_link_plugin import D75Plugin` resolved to the **stale copy** at `/home/user/link/d75_link_plugin.py` (May 6) instead of the fresh `/home/user/link/run/d75_link_plugin.py` (May 19).

The stale parent-dir copy had been there since an earlier deployment style. The pyc cache at `/home/user/link/__pycache__/d75_link_plugin.cpython-313.pyc` reinforced this — Python kept loading the bytecode of the stale .py.

md5sums matched between local repo and `/home/user/link/run/` so we wrongly believed the deploys were taking effect.

## How we found it

Asked the user to commit to instrumentation (not more guesses). Wrote a `[D75-WD] thread STARTED` print at the very first line of `_watchdog()` so the thread starting was undeniable. Deployed, restarted plugin, watched journal: **still nothing**. That print could only fail to appear if the thread never executed `_watchdog`, which meant the import was loading a different file. `find /home/user -name d75_link_plugin*` revealed the duplicate.

## Fix

Two changes shipped in commit `2821537`:

1. **`tools/link_endpoint.py`** — now inserts BOTH `run/` and parent into `sys.path`, with `run/` last so it lands at index 0 and wins. Comment in the file warns the next reader why the order matters.
2. **Heavy `[D75-WD]` / `[Serial-DROP]` instrumentation** — per-tick log of `serial_ok` + `rx_alive`, state-transition markers, watchdog thread lifecycle (start + exit), explicit logs at every `_connected = False` point in `SerialManager._read_loop` and `send_raw`.

Also on the live Pi (.123):
- Copied `run/d75_link_plugin.py` and `run/remote_bt_proxy.py` over their stale parent-dir twins to make the deploy immediately effective.
- Removed `/home/user/link/__pycache__/d75_link_plugin.cpython-313.pyc` and `remote_bt_proxy.cpython-313.pyc`.

## What the journal looks like now (verified working)

```
[D75-WD] thread STARTED — interval=10s, thread_name=D75-Watchdog
[D75-WD] tick #1 serial=True rx=True _serial_obj=set _audio_obj=set
[D75-WD] tick #2 serial=True rx=True _serial_obj=set _audio_obj=set
...
```

When the next drop occurs we will get:
- `[D75-WD] STATE CHANGE serial: True → False (at tick N)`
- `[Serial-DROP] _read_loop: recv() returned empty (peer closed RFCOMM ch2) → marking serial disconnected` *or* `[Serial-DROP] _read_loop: BrokenPipeError: ...` etc.
- `[D75-WD] tick #N+1 serial=False rx=True ...` — watchdog detected
- `[D75-WD] serial lost, audio alive — serial-only reconnect` — recovery attempt
- Either reconnect success or escalation to full BT reconnect

## How to apply

- When a "fix" doesn't change observable behaviour, **prove the new code is running** before iterating on it. A single `print("VERSION X reached")` at function entry would have caught this six weeks earlier.
- Deploys to subdirectories require Python's import resolution to be set up so the deploy target wins over any legacy copies. Either delete the legacy copies, or insert the deploy dir at `sys.path[0]`.
- For Pi-side debugging, `find /home/user -name <file>` and `ls __pycache__` are quick safety checks when a deployed file "isn't behaving as expected."
